## 1. 开场（30 秒）

各位老师好，我的毕业设计题目是《面向开发者的 bug 协作平台的设计开发》。  
本项目聚焦一个现实痛点：开发者在跨项目 Bug 处理时，常出现匹配效率低、经验难复用、线上沟通难落地的问题。  
我实现了一个“用户端 + 管理端 + 后端服务 + 共享包”的完整平台，并围绕“线上匹配 + 线下协作 + 人工运营”进行了工程化落地。

---

## 2. 研究背景与目标（1 分钟）

### 2.1 背景问题

- 现有工具（如 Issues）更偏项目内协作，不适合跨项目 Bug 对接。
- 纯社区问答缺少状态流转、承接关系和时效治理。
- 线上沟通无法覆盖真实调试场景，落地效率偏低。

### 2.2 本项目目标

- 让用户可以发布、承接、跟进 Bug；
- 让管理员可以做时效治理、人工介入、日志审计；
- 保证系统在可维护、可扩展的前提下可落地运营。

---

## 3. 系统总体方案（2 分钟）

### 3.1 技术架构

- 前端：Vue3 + Vite + Pinia + Vue Router  
- 后端：NestJS + TypeORM + MySQL + JWT  
- 工程化：pnpm + Turbo（monorepo）  
- 共享层：`@bug/shared` 统一类型、枚举和响应结构

### 3.2 多端职责

- `fe-h5`：普通用户侧，负责发布/承接/列表/详情/个人中心  
- `fe-admin`：运营治理侧，负责订单监管、用户管理、时效规则、操作日志  
- `be-main`：统一业务服务层，提供 API、鉴权、定时任务与数据持久化

### 3.3 为什么采用 monorepo

- 前后端共享类型，降低联调成本；
- 多包统一依赖与构建，改动链路更清晰；
- 便于后续扩展新端或新模块。

---

## 4. 核心业务流程（2 分钟）

### 4.1 用户侧（H5）

1. 登录并获得 JWT；  
2. 发布 Bug（标题、技术栈、描述、预期效果）；  
3. 其他用户承接（仅 `PENDING` 可承接）；  
4. 进入沟通状态并更新进度；  
5. 形成“我发布的/我承接的”闭环记录。

### 4.2 管理侧（Admin）

1. 管理员登录并进入后台；  
2. 查看订单列表与时效状态；  
3. 配置时效规则（预警/超期小时）；  
4. 对异常订单做人工介入；  
5. 在操作日志中完成审计追踪。

### 4.3 风控闭环

- 定时任务每 5 分钟扫描符合规则的订单；
- 将订单标记为正常/预警/超期；
- 运营按状态集中处理，关键操作全留痕。

---

## 5. 关键实现亮点（3 分钟）

### 5.1 鉴权与权限分层

- JWT 无状态鉴权，前端统一携带 `Authorization: Bearer <token>`；
- 后端 `JwtStrategy + Guard` 完成身份校验；
- `RolesGuard` 完成角色级权限控制（`USER` / `ADMIN` / `SUPER_ADMIN`）。

### 5.2 Bug 列表高效筛选

- 支持技术栈、状态、时效状态、关键词、分页组合筛选；
- 采用 TypeORM QueryBuilder 动态拼接条件；
- 对高频字段建立索引，保障查询性能。

### 5.3 时效监控任务

- 基于 `@nestjs/schedule` 定时执行；
- 规则配置化（`warnHour`、`expireHour`）；
- 自动计算并更新 `time_status`，支撑运营治理。

### 5.4 可追溯审计

- 发布、承接、状态变更、人工介入等关键动作写入 `operation_log`；
- 支持按操作人、类型、时间筛选；
- 满足后续纠纷处理和运营审计需求。

---

## 6. 数据库设计（1 分钟）

核心表共 4 张：

- `user`：账号、角色、状态、联系方式  
- `bug`：发布/承接关系、状态、时效状态、备注  
- `operation_log`：关键操作日志  
- `time_rule`：时效规则配置

关系特点：

- `user` 与 `bug` 一对多（发布/承接）；
- `bug` 与 `operation_log` 一对多；
- `time_rule` 通过状态类型驱动 `bug` 的时效计算。

### 7.1 测试覆盖

- 功能测试：注册登录、发布承接、状态流转、后台管理；
- 流程测试：从发布到人工介入全链路；

- 时效测试：预警/超期标记准确性；

- 兼容性测试：多浏览器与多终端访问。

### 7.2 结果总结

- 核心流程可闭环执行；
- 权限控制有效；

- 具备上线后的运营治理基础能力。

## 8. 创新点与不足（1 分钟）

### 8.1 创新点

- 将“社区匹配 + 人工运营 + 时效治理”融合到同一平台；
- 不是仅做信息发布，而是做可追踪、可干预的协作闭环；
- 通过共享包与 monorepo 强化前后端一致性。

### 8.2 当前不足

- 社群联动仍偏人工，自动化通知不足；
- 数据分析维度还不够深；
- 生产级高可用架构仍需进一步增强。

## 附：答辩高频问答（可直接背诵）

### Q1：为什么不用微前端？

当前核心目标是“高效复用与快速落地”，monorepo + shared 已满足；微前端更适合多团队独立部署场景，当前阶段引入会增加运行时复杂度与运维成本。

### Q2：为什么选择 NestJS？

NestJS 模块化和依赖注入能力强，便于按 User/Auth/Bug/Admin 拆分；同时与 TypeScript 配合好，适合多人协作和后期维护。

### Q3：时效监控为什么用定时任务，不用实时？

该业务对秒级实时性要求不高，采用“每 5 分钟扫描”可显著降低系统复杂度和资源消耗，并满足运营处理时效。

### Q4：系统安全性如何保证？

采用 JWT 鉴权、角色守卫、参数校验、密码加密存储，并对关键操作进行日志留痕，形成“认证 + 授权 + 审计”三层防护。

### Q5：如果用户量增大，如何扩展？

前端可静态化 + CDN，后端可服务集群化，数据库做主从和读写分离；热点查询可加 Redis 缓存，并继续优化索引与分页策略。
